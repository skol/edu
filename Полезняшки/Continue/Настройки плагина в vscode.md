При использовании плагина **Continue** в **VS Code** правила (rules) хранятся в рабочей директории проекта внутри папки **`.continue/rules/`**. [1](https://docs.continue.dev/customize/rules), [2](https://continue-docs.mintlify.app/customize/deep-dives/rules)

# Какие файлы и как настраивать

Все файлы правил создаются в формате **Markdown (`.md`)** (а также могут содержать опциональный YAML-заголовок — frontmatter в начале файла). Вы можете создать любое количество файлов с произвольными названиями (например, `typescript-rules.md`, `testing-style.md`, `security-guidelines.md`). [1](https://continue-docs.mintlify.app/customize/deep-dives/rules), [2](https://cursor-alternatives.com/blog/continue-dev-rules/)

## Структура файла правила (`.md`)

Каждый файл в папке `.continue/rules/` обычно состоит из двух частей:

- **YAML Frontmatter (метаданные в начале файла):**
    - `name` — отображаемое имя правила в интерфейсе.
    - `alwaysApply` — булево значение (`true` / `false`): если `true`, правило подмешивается в системный промпт при каждом запросе; если `false` или не указано, правило применяется динамически.
    - `globs` — шаблон путей файлов (например, `"**/*.ts"` или `["**/*.ts", "**/*.tsx"]`), при работе с которыми это правило активируется.
    - `regex` — регулярное выражение для активации правила при определенном содержимом файлов.
    - `description` — краткое описание назначения правила. [1](https://continue-docs.mintlify.app/customize/deep-dives/rules), [2](https://cursor-alternatives.com/blog/continue-dev-rules/)

- **Основное содержимое (Markdown):**
    - Текстовые инструкции для языковой модели (LLM): жесткие требования (ALWAYS / NEVER), примеры кода (позитивные и негативные), соглашения по именованию или архитектурные ограничения. [1](https://www.sitepoint.com/automated-style-guides-enforcing-coding-standards-with-continue-ci/)
## Альтернативные или связанные конфигурационные файлы

Помимо папки `.continue/rules/`, поведение Continue в VS Code управляется основными файлами конфигурации:

- **`config.yaml`** (или устаревший `config.json`) в глобальной папке (`~/.continue/`) или в корне рабочей области (`.continue/config.yaml`), где настраиваются модели, промпты и глобальные параметры.
- **Промпты (`.continue/prompts/` или секция `prompts` в конфиге)** — файлы для переиспользуемых команд (`/slash-commands`), которые отличаются от правил тем, что вызываются пользователем целенаправленно. [1](https://docs.continue.dev/customize/deep-dives/prompts), [2](https://cursor-alternatives.com/blog/continue-dev-rules/), [3](https://docs.continue.dev/guides/configuring-models-rules-tools)

Вот **оптимальная, рабочая конфигурация** для плагина **Continue** в **VS Code**, без лишнего хайпа и «навырост». Она «заточена» под полную изоляцию, разделение обязанностей между моделями и ваш стек (Python/CLI/FastAPI + Vue.js/Shadcn). [1](https://habr.com/ru/articles/938036/), [2](https://routerai.ru/pages/vibe-coding-vscode-continue), [3](https://habr.com/ru/news/757434/)

Поскольку вы используете **Qwen Coder** и **Llama Coder**, лучшим разделением труда будет:

- **Чат и Редактор (Ctrl+L / Ctrl+I):** `Qwen2.5-Coder` (редакции 7B/14B/32B в зависимости от железа) — на данный момент она лучшая по контексту и архитектурным вопросам.
- **Автодополнение (Tab):** `Llama-3.1-Coder-3B` (или `Qwen2.5-Coder-1.5B/3B`) — они молниеносны, что критично для inline-дополнения.

### Шаг 1: Глобальный конфиг `config.yaml`

Откройте настройки Continue (значок шестеренки внизу панели чата). Замените содержимое на чистый рабочий YAML, адаптированный под локальный сервер (например, **Ollama** или **LM Studio**). [1](https://docs.continue.dev/customize/deep-dives/configuration), [2](https://routerai.ru/pages/vibe-coding-vscode-continue), [3](https://itcodik.com/article/lokalnyy-chatgpt-v-vs-code), [4](https://habr.com/ru/articles/938036/)

_Если модели вынесены на соседний ПК, замените `localhost` на его локальный IP (например, `192.168.1.50`)._
```yaml
# ~/.continue/config.yaml
version: 1.0.0
models:
  # Основная модель для чата (Ctrl+L) и рефакторинга (Ctrl+I)
  - name: Qwen2.5-Coder-14B
    provider: ollama # или lmstudio
    model: qwen2.5-coder:14b # имя модели в вашей системе
    roles:
      - chat
      - edit

tabAutocompleteModel:
  # Легкая и быстрая модель для Tab-комплита
  name: Llama-3.1-Coder-3B
  provider: ollama
  model: llama3.1-coder:3b

# Оптимальные контекст-провайдеры (без перегрузки памяти)
contextProviders:
  - name: file
    params: {}
  - name: codebase # Индексирует проект локально, незаменим для FastAPI/Vue связок
    params: {}
  - name: open
    params: {}

# Реально полезные слэш-команды
slashCommands:
  - name: edit
    description: Редактировать выделенный код
  - name: comment
    description: Написать понятный docstring / jsdoc
  - name: share
    description: Экспорт диалога
```
### Шаг 2: Настройка файлов в папке `.continue/rules/`

Чтобы модели не путали архитектурные подходы CLI-приложений и веб-фронтенда, мы разделяем инструкции с помощью **Frontmatter (globs)**. Создайте эти файлы в корне вашего проекта. [1](https://continue-docs.mintlify.app/customize/deep-dives/rules), [2](https://cursor-alternatives.com/blog/continue-dev-rules/)

## 1. Общие правила для всего проекта

Поскольку вы не хотите сюрпризов, принудительно задаем лаконичный стиль ответов для локальных моделей. [1](https://www.sitepoint.com/automated-style-guides-enforcing-coding-standards-with-continue-ci/)
```markdown
<!-- .continue/rules/00-global.md -->
---
name: Global Code Style
alwaysApply: true
description: Базовые требования к генерации кода
---
- ALWAYS пиши код без лишних вводных слов, пояснений и "воды". Только суть.
- NEVER генерируй огромные простыни кода, если изменилась одна строка. Показывай только изменения или диффы.
- Пиши комментарии и docstrings строго на русском языке.
```
## 2. Правила для бэкенда (Python + FastAPI + CLI)

Правило активируется автоматически, только когда вы открываете `.py` файлы. Защищает от генерации старых подходов. [1](https://continue-docs.mintlify.app/customize/deep-dives/rules), [2](https://cursor-alternatives.com/blog/continue-dev-rules/)
```markdown
<!-- .continue/rules/python-backend.md -->
---
name: Python Backend Conventions
globs: ["**/*.py"]
description: Стандарты для FastAPI и Typer CLI
---
При работе с Python-кодом строго соблюдай:

1. **FastAPI**:
   - Используй современный синтаксис `Annotated` для Dependency Injection (например, `repo: Annotated[UserRepository, Depends()]`).
   - Возвращай Pydantic-схемы (v2) во всех `response_model`.
   - Асинхронные эндпоинты (`async def`) только там, где есть реальный асинхронный I/O. Если библиотека синхронная (например, старый psycopg2) — пиши `def`.

2. **CLI**:
   - Используй библиотеку `typer` для построения CLI интерфейсов.
   - Обязательно типизируй аргументы командной строки через `typer.Argument` и `typer.Option`.

3. **Типизация**:
   - Строгая типизация во всех сигнатурах функций. Никаких `Any`, где это возможно.
```

## 3. Правила для фронтенда (Vue.js + Shadcn/ui)

Так как вы только осваиваете **shadcn/ui**, это правило заставит модель использовать именно его компоненты, а не писать CSS велосипеды. [1](https://designmd.app/guides/continue-dev)
```markdown
<!-- .continue/rules/vue-frontend.md -->
---
name: Vue Frontend Standards
globs: ["**/*.vue", "**/*.ts", "**/*.js"]
description: Правила для Vue 3 Composition API и Shadcn
---
При генерации фронтенд-кода следуй инструкциям:

1. **Vue 3**:
   - Используй исключительно `<script setup>` и TypeScript.
   - Избегай прямого изменения реактивного состояния из дочерних компонентов (строго через `defineEmits`).

2. **Shadcn/ui и Tailwind**:
   - Модели ОЧЕНЬ любят писать инлайн-стили или чистый CSS. Запрещено: ALWAYS используй утилитарные классы Tailwind CSS.
   - Вместо создания кастомных кнопок, модалок или инпутов, используй компоненты из `@/components/ui/` (стандартный алиас путей shadcn).
   - Если нужного компонента shadcn нет в контексте, спроси меня, установлен ли он, прежде чем верстать его вручную.
```

## Тонкие настройки под особенности Qwen и Llama Coder

1. **Контекстное окно (Память):** Локальные модели (особенно 7B/14B) при забивании контекста начинают «тупеть» или бесконечно повторять код.
    - _Решение:_ Держите чат чистым. Обсудили функцию в `Ctrl+L` -> нажмите значок «+» (New Session), чтобы стереть историю и вернуть модели максимальную точность. [1](https://routerai.ru/pages/vibe-coding-vscode-continue)
2. **FIM (Fill-in-the-Middle) для автодополнения:** `Llama-3.1-Coder` и `Qwen2.5-Coder` превосходно понимают контекст «до» и «после» курсора. Опция `tabAutocompleteModel` в Continue по умолчанию правильно конфигурирует шаблоны для Ollama, поэтому в `config.yaml` не нужно прописывать сложные `promptTemplates` вручную — плагин сам определит токены `PRE`/`SUF` для этих моделей. [1](https://itcodik.com/article/lokalnyy-chatgpt-v-vs-code)
3. **Разделение по машинам:** Если выносите модели на соседний ПК с мощной видеокартой, обязательно убедитесь, что в конфиге Ollama/LM Studio на той машине прописан хост `0.0.0.0` (разрешить входящие подключения), иначе Continue на основном ПК будет ловить `Connection Refused`. [1](https://itcodik.com/article/lokalnyy-chatgpt-v-vs-code)

Чтобы локальная база знаний (**`@codebase`**) работала быстро и не забивала память контекста моделей мусором, нужно правильно настроить игнорирование файлов. Continue использует стандартный `.gitignore`, но часто в него забывают добавить вещи, которые человеку не мешают, а локальный эмбеддинг-движок (LanceDB, работающий прямо в VS Code) просто «вешают».

## Тонкая настройка через `.continueignore` (Если нужно еще точнее)

Если в `.gitignore` вы не хотите что-то добавлять (например, папки с автодокументацией или локальными JSON-дампами данных для тестов CLI), вы можете создать в корне проекта отдельный файл **`.continueignore`**. Он работает точно так же, но влияет _только_ на плагин Continue.

### **Рекомендуемое содержимое `.continueignore`:**
```text
# Игнорируем автосгенерированную документацию бэкенда (модель и так знает FastAPI)
site/
docs/

# Игнорируем тяжелые JSON/CSV файлы данных, на которых вы тестируете CLI
data/*.json
data/*.csv
tests/fixtures/

# Игнорируем собранные файлы фронтенда, если они лежат внутри папки бэкенда
**/static/dist/
```

Как проверить, что всё работает без зависаний?

1. После настройки файлов перезапустите VS Code.
2. Откройте панель Continue и введите в чат `@codebase`. Начнется индексация (в правом нижнем углу появится прогресс-бар).
3. Благодаря чистке от `node_modules` и `.venv` индексация даже на слабом ПК займет **всего 10–30 секунд** вместо зависания на полчаса.

Секрет 100% эффективности локальных моделей (особенно специализированных Coder-версий) — это **контекст, структура и жесткие ограничения**. С включенным `@codebase` вам больше не нужно копировать код руками.

Вот 3 шаблона готовых промптов («золотой стандарт»), которые гарантированно работают с вашим стеком. Скопируйте их в блокнот или прямо в `.continue/prompts/`.

## 1. Добавление нового эндпоинта (FastAPI)

**Проблема:** Модель часто забывает импортировать нужные схемы, путает асинхронность или генерирует не тот формат ответа.  
**Промпт (вставлять в Чат, Ctrl+L):**
```text
@codebase @app.py @schemas.py (выберите файлы вашего API и схем через @)
Мне нужно добавить новый эндпоинт для [КРАТКОЕ ОПИСАНИЕ, например: удаления пользователя по ID].

Действуй по шагам:
1. Найди существующий роутер для этой сущности.
2. Создай Pydantic-схему ответа, если её нет в контексте, строго следуя стилю проекта (Pydantic v2).
3. Напиши сам эндпоинт. Используй Annotated для внедрения зависимостей (бд, сессии).
4. Напиши только код изменений (diff) или чистый новый блок кода без лишнего текста.
```
## 2. Связка Бэкенда и Фронтенда (FastAPI -> Vue + Shadcn)

**Проблема:** Модель выдумывает пути к API, неправильно парсит JSON или пишет реактивность «по-старому».  
**Промпт (вставлять в Чат, Ctrl+L):**
```text
@codebase @router.py @Component.vue (укажите файл роутера FastAPI и Vue-компонент, который будет слать запрос)
Мне нужно связать этот бэкенд-роут с фронтендом. Создай или обнови Vue-компонент.

Требования:
- Используй `<script setup lang="ts">`.
- Для запроса используй axios/fetch (как принято в проекте). Вынеси интерфейс ответа (TypeScript interface) строго на основе Pydantic-модели из роутера.
- Для верстки используй Tailwind. Если нужны элементы интерфейса (кнопки, инпуты), бери их из `@/components/ui/` (shadcn), не пиши сырые теги.
- Выведи состояние загрузки (loading) и обработку ошибок.
```
## 3. Написание новой CLI команды (Typer)

**Проблема:** Локальные модели путают синтаксис `click` и `typer` или генерируют некрасивый вывод в терминал.  
**Промпт (вставлять в Чат, Ctrl+L):**
```text
@codebase @cli.py 
Добавь новую команду в этот CLI интерфейс. Название команды: `[например: import-data]`.
Аргументы: `[например: path: путь к файлу, --force: флаг перезаписи]`.

Правила:
- Используй `typer.Argument` и `typer.Option` с explicit-типизацией.
- Добавь help-тексты к аргументам на русском языке.
- Для вывода красивого текста в консоль (успех/ошибка) используй `rich` (если он есть в проекте) или стандартный `typer.secho` с цветами (fg=typer.colors.GREEN).
```

## 💡 4 главных правила, чтобы поднять эффективность до 80-90%:

1. **Правило «Одного действия»:** Никогда не просите в одном промпте: _«Сделай модель в бд, роут к ней, CLI команду и фронтенд»_. Локальная модель сломается на втором шаге. Сначала попросите сделать схему -> утвердите -> следующим промптом попросите сделать роут на основе схемы.
2. **Якоря контекста (Символ `@`):** Модель ленива. Если написать просто `@codebase`, она будет искать по всему проекту и может зацепить старый код. Всегда явно дописывайте через `@` ключевые файлы (`@main.py`, `@index.vue`), чтобы направить её фокус.
3. **Запрет на разговорчики:** Если модель начинает писать лекции вместо кода, просто добавьте в конец промпта фразу: **«WRITE CODE ONLY. NO EXPLANATIONS.»** (на английском локальные модели понимают такие приказы жестче).
4. **Используйте встроенный Редактор (Ctrl+I):** Если нужно изменить конкретный кусок кода в открытом файле — не пишите в чат. Выделите этот кусок мыheadшкой, нажмите `Ctrl+I` и напишите короткую команду (например: _«Перепиши этот метод на async и добавь try-except»_). Модель заменит код прямо в файле, подсветив изменения как в Git.

«Всё одной кнопкой» (полная автоматизация) и «всё просто и управляемо» (точечный контроль) — это классический маятник в разработке. Чтобы глаза перестали разбегаться, этот пайплайн нужно строить не вокруг абстрактных возможностей ИИ, а вокруг **вашего личного workflow**.

Вот прагматичный, «бесхайповый» подход к тому, как подружить локальный ИИ со своей рутиной, не теряя контроля:

---

1. Архитектурный подход: ИИ как изолированная CLI-утилита

Поскольку вы пишете CLI-приложения, представьте ИИ-ассистента просто как еще одну CLI-команду в вашем терминале. У неё есть четкий `input` (контекст вашего файла) и четкий `output` (измененный код).

- **Как контролировать:** Не давайте модели менять файлы напрямую без вашего одобрения. Плагин Continue в режиме `Ctrl+I` как раз работает как интерактивный `git diff`. Вы видите каждую строчку, которую она хочет вставить, и можете нажать `Accept` или `Reject`. Это идеальный баланс между «быстро» и «управляемо».

2. Принцип «Атомарных шагов» (Анти-пайплайн)

Забудьте про сложные агентские пайплайны, которые обещают «написать приложение по одному текстовому описанию». На практике они генерируют тонны технического долга.

Разбейте разработку фичи на **3 жестких, изолированных этапа**, где на каждом этапе вы полностью контролируете результат:

```
[Этап 1: Проектирование] ──> Вы одобряете схему/интерфейс 
      │
[Этап 2: Логика бэкенда] ──> Вы запускаете тесты/CLI, проверяете работу
      │
[Этап 3: Фронтенд]       ──> Вы натягиваете интерфейс на рабочий API
```

- На **Этапе 1** ИИ помогает набросать типы (Pydantic или TypeScript). Вы смотрите на них свежим взглядом. Если архитектура кривая — правите руками.
- На **Этапе 2** вы скармливаете ИИ утвержденные типы и просите написать логику.
- На **Этапе 3** вы даете фронтенд-модели готовый роут бэкенда.

Каждый шаг прост, управляем, и у вас никогда не возникнет ситуации, когда «код написан, но ничего не работает и непонятно почему».

3. Где автоматизация «одной кнопкой» РЕАЛЬНО работает

Не тратьте время на автоматизацию написания бизнес-логики. Автоматизируйте **рутину**, которую вы ненавидите и где сложно ошибиться:

- **Генерация тестов:** Написали сложную функцию валидации в FastAPI? Выделили, нажали `Ctrl+I` -> _«Напиши 5 pytest тестов, включая edge cases»_. Это экономит часы.
- **Документация и Docstrings:** Написали CLI-команду? Попросите модель сгенерировать понятный `--help` текст или docstring по стандарту Google.
- **Рутинный маппинг:** Переписать Pydantic-модель в TypeScript-интерфейс для Vue. Для человека это 10 минут скучного копипаста, для Qwen/Llama — 2 секунды.

---

В **Continue** есть штатные, невероятно удобные механизмы для создания собственной коллекции динамических сниппетов, которые работают без хайпа и сторонних плагинов (вроде Context7) прямо через `Ctrl+I` или `Ctrl+L`.

Для вашей задачи — вставить готовый, адаптированный под проект шаблон в одно нажатие — лучше всего подходят два встроенных инструмента: **Custom Prompts** (Кастомные промпты) и **Slash Commands** (Слэш-команды).

Вот как это настроить для вашего примера с подключением к БД.

---

### Вариант 1. Слэш-команды (Slash Commands) — Самый быстрый путь

Вы можете создать команду `/db`, которая при вызове через `Ctrl+I` будет мгновенно генерировать нужный шаблон, зная контекст вашего проекта.

Откройте ваш глобальный или локальный **`config.yaml`** и добавьте секцию `customCommands`:

```yaml
# .continue/config.yaml
customCommands:
  - name: db
    description: "Вставить шаблон подключения к БД (FastAPI + SQLAlchemy/Tortoise)"
    prompt: |
      Напиши стандартный код инициализации подключения к базе данных.
      Используй SQLAlchemy (AsyncSession), если в проекте используется она, либо Tortoise-ORM (сверяйся с контекстом, если он есть).
      Строка подключения ДОЛЖНА считываться из файла `.env` через settings (pydantic-settings), например: `settings.DATABASE_URL`.
      Выведи ТОЛЬКО чистый код подключения, без лишних разговоров.
```
**Как это работает на практике:**

1. Вы ставите курсор в нужное место файла (или выделяете пустую строку).
2. Нажимаете **`Ctrl+I`**.
3. Пишете **`/db`** (Continue сам подставит описание) и нажимаете **Enter**.
4. Модель генерирует готовый блок кода прямо в файл, а вы нажимаете `Accept` (или `Ctrl+Enter`).

---

### Вариант 2. Папка `.continue/prompts/` — Шаблоны «на стероидах»

Если вы хотите иметь полноценную коллекцию сниппетов, которую можно версионировать в Git вместе с проектом, используйте файлы промптов. Это те же сниппеты, но они могут принимать системный контекст.

1. Создайте файл **`.continue/prompts/db-connect.prompt`** в корне проекта.
2. Напишите в него шаблон-инструкцию:
```text
---
name: db
description: Вставить подключение к БД из env
---
Напиши код подключения к базе данных для этого проекта. 

Условия:
1. Подключение должно использовать async/await.
2. Параметры подключения (DATABASE_URL) берутся строго из `.env` через объект конфигурации.
3. Добавь базовый try-except блок для проверки соединения при старте.

Выведи только код. Никакого текста вокруг.
```
#### **Как это работает:**  
Точно так же: нажимаете `Ctrl+I`, вводите `/db`, и Continue берет инструкцию из этого файла. Плюс в том, что у вас в папке `prompts/` может лежать аккуратная коллекция: `db.prompt`, `auth.prompt`, `vue-table.prompt` и т.д.

---

### Почему это лучше обычных сниппетов VS Code?

Обычные сниппеты VS Code (`json`-файлы) статичны — они просто вставляют жесткий текст, где вам потом надо вручную менять имена переменных.

Сниппеты через Continue:

- **Адаптируются под проект:** Если у вас в соседнем файле настройки Pydantic называются `Config`, модель напишет `Config.DB_URL`. Если `Settings` — она напишет `settings.DATABASE_URL`.
- **Понимают стек:** Модель посмотрит на импорты в файле и поймет, пишете вы на Asyncpg, SQLAlchemy или SQLModel, и сгенерирует код в нужном стиле.

Вот три готовых, «бесхайповых» шаблона для вашей папки **`.continue/prompts/`**. Создайте их прямо в проекте:

## 1. Роут авторизации / защиты (FastAPI)

Этот сниппет нужен, когда создается новый закрытый эндпоинт, и туда нужно быстро прокинуть текущего пользователя через Dependency Injection, не вспоминая точный синтаксис зависимостей.

Создайте файл **`.continue/prompts/auth-route.prompt`**:
```text
---
name: auth
description: Добавить проверку JWT / текущего пользователя в роут FastAPI
---
Добавь в текущую функцию (или создай шаблон эндпоинта) проверку авторизации пользователя через зависимости (Depends).

Условия:
1. Используй существующую в проекте функцию получения текущего пользователя (например, get_current_user, get_current_active_user) и Annotated.
2. Если зависимости нет в контексте, напиши стандартную заглушку зависимости, которая парсит JWT токен.
3. Роут должен возвращать HTTP 401 Unauthorized, если токен невалиден или просрочен.
4. Выведи только измененный/новый код. Без лишнего текста.
```

## 2. Типовая CLI-команда (Typer)

Сниппет для быстрого разворачивания каркаса новой команды в CLI-интерфейсе, чтобы не писать руками бойлерплейт с декораторами.

Создайте файл **`.continue/prompts/cli-cmd.prompt`**:
```text
---
name: clicmd
description: Создать каркас новой CLI-команды Typer
---
Создай каркас новой команды для нашего CLI-приложения на Typer.

Условия:
1. Используй декоратор существующего в файле Typer-аппа (например, @app.command()).
2. Добавь один обязательный аргумент и один опциональный флаг (--force или --dry-run) с помощью typer.Argument и typer.Option.
3. Добавь docstring на русском языке (он станет help-текстом в терминале).
4. Внутри функции добавь базовый блок try-except и вывод успешного завершения через typer.secho или rich.
5. Выведи только код команды.
```
## 3. Базовая форма (Vue 3 + Shadcn/ui)

Этот шаблон решает главную проблему фронтенда: когда лень руками импортировать инпуты, кнопки и связывать их с `v-model`.

Создайте файл **`.continue/prompts/vue-form.prompt`**:
```text
---
name: form
description: Сгенерировать форму на Vue 3 с компонентами Shadcn
---
Создай или вставь в компонент форму для отправки данных.

Условия:
1. Используй `<script setup lang="ts">` и реактивное состояние через `ref` или `reactive`.
2. Посмотри, какие компоненты из `@/components/ui/` (button, input, label, card) уже используются в проекте или импортируй их в стиле shadcn/ui.
3. Стилизуй форму через Tailwind CSS (компактная карточка, отступы gap-4, фокус-состояния).
4. Добавь обработчик @submit.prevent, который вызывает функцию отправки и блокирует кнопку во время загрузки (isSubmitting).
5. Никакого сырого CSS. Только чистый шаблон и скрипт.
```

## Как теперь этим пользоваться:

1. Пригнали курсор в нужное место файла.
2. Нажали **`Ctrl+I`**.
3. Ввели слэш и имя сниппета: **`/auth`**, **`/clicmd`** или **`/form`**.
4. Нажали **Enter** и оценили результат.

Инструменты настроены, база данных (`@codebase`) готова к локальному сканированию, а сниппеты теперь умные.

Локальные модели, особенно **Qwen 2.5 Coder**, воспринимают формат **Swagger/OpenAPI** просто **великолепно**. Для LLM структурированный JSON или YAML — это гораздо более понятный и однозначный контекст, чем размытое текстовое описание.

Подача задачи через Swagger решает сразу несколько проблем:

1. **Никакой двусмысленности:** Модель сразу видит точные типы данных, query-параметры, обязательные поля и коды ответов (200, 400, 404). Она не будет выдумывать структуру Pydantic-схем на ходу.
2. **Идеально для SQLAlchemy Core:** Так как вы явно просите использовать асинхронную `sqlalchemy.core` (без ORM-моделей и `relationship`), модель свяжет поля из Swagger напрямую с объектами `Table` и методами `select()`, `insert()`, `update()`. Для нее это превращается в простую задачу «маппинга» (перекладывания данных из схемы в SQL-выражение).

Оптимальный шаблон промпта для этого сценария:

Если у вас есть кусок Swagger (OpenAPI) спецификации, вы можете скармливать его прямо в `Ctrl+I` или `Ctrl+L` по следующему шаблону:

text

```
Используя этот фрагмент OpenAPI/Swagger спецификации:
[ВСТАВИТЬ КУСОК JSON/YAML ИЗ SWAGGER]

Напиши эндпоинт FastAPI и функции для работы с БД.
Жесткие условия:
1. Используй строго асинхронный синтаксис (async/await).
2. Для БД используй только SQLAlchemy Core (объекты Table, async_session.execute()). Полная ORM запрещена.
3. Сгенерируй соответствующие Pydantic v2 схемы для запроса и ответа на основе Swagger.
```

Используйте код с осторожностью.

Модель выдаст чистый, прямолинейный и очень производительный код, так как архитектура Core + FastAPI ей интуитивно понятна, а рамки жестко заданы спецификацией.

Чтобы навсегда избавить себя от генерации ненужных таблиц и миграций, добавьте это жесткое ограничение прямо в ваше бэкенд-правило **`.continue/rules/python-backend.md`** (которое мы создали в самом начале).

Просто допишите туда блок для Core:

markdown

```
3. **SQLAlchemy Core (Без ORM)**:
   - NEVER генерируй новые таблицы (`Table`), метаданные (`MetaData`) или миграции Alembic на основе Swagger-схем.
   - Воспринимай типы из запросов/Swagger как **уже существующие поименованные запросы (subqueries), представления (Views) или готовые выборки**.
   - Пиши только логику выборки через `select()`, `where()` и выполнение через `async_session.execute()`, используя существующие структуры данных.
```

Используйте код с осторожностью.

Теперь, когда вы будете вызывать модель через `Ctrl+I` или чат, это правило будет автоматически подмешиваться к её «сознанию». Она поймет, что база данных уже спроектирована до неё, а её задача — просто написать правильный асинхронный SQL-запрос поверх ваших именованных сущностей.

## 💡 Лайфхак для удобства

Чтобы каждый раз не копировать огромный Swagger в чат, вы можете сохранить его (или его часть) прямо в проекте как временный файл (например, `api-schema.json`), и просто призывать его через `@api-schema.json`. Локальная Qwen/Llama мгновенно сопоставит два файла в контексте и выдаст вам четкий аудит.
